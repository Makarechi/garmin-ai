# Задание Codex: продукт для новых пользователей и контрибьюторов

## Контекст и scope

Изучить текущий main и этот пакет. Основа исследования — `8d9bd0208da5891f836ce7045004ef729fa40aab`; если HEAD изменился, сначала обновить фактическую матрицу, не откатывать новые исправления.

Цель — self-hosted приложение с пользовательскими трекерами, источниками данных, необязательными мессенджерами и AI, пригодное чужому пользователю и независимому контрибьютору. Garmin и Telegram сохранить. WhatsApp и Viber сейчас не реализовывать. Не превращать задачу в переименование всего проекта, переход на другой стек или SaaS.

Материалы — аналитический handoff, не утверждение, что предложенные команды, пути examples или SDK уже существуют. Этот документ сам по себе не разрешает публиковать лицензию от имени владельца, подключать реальные сервисы, тратить API quota, менять доступы GitHub или выкладывать личные данные.

## Первый законченный результат

Подготовить один сфокусированный этап, который превращает текущие capabilities в проверяемый путь расширения:

1. Зафиксировать SHA, текущие публичные возможности и оставшиеся runtime provider branches.
2. Спроектировать минимальное развитие существующего registry до реального lifecycle (CP-03), не создавая второй runtime.
3. Сохранить совместимость старой .env и именованных интеграций, consent/pause/fencing, safe retries и single-owner ограничения.
4. Добавить отдельный синтетический plugin fixture, который обнаруживается и явно включается конфигурацией, проходит normal lifecycle и получает только свой validated config/secret reference.
5. Проверить, что установка/отключение/ошибка этого плагина не ломают core без SDK и не делают внешних вызовов.
6. Описать публичные контрактные типы и реальные команды воспроизведения. Не объявлять весь CP-03 завершённым, если переведена только одна часть lifecycle.

Начать с описания критериев и тестов, затем менять код. Не компенсировать большой refactor только проверкой импорта. Добавить assertions о реально вызванных factory/handler, idempotent operation и отдельном состоянии каждого instance.

## Параллельная короткая работа без runtime-риска

Предложить владельцу license decision; после явного выбора действовать в рамках прав на код. Подготовить новый человеческий CONTRIBUTING и карту публичных путей, но не ослаблять существующие требования безопасности. Установленные maintainers определяют merge policy.

Уточнить CP-04/05 как отдельные PR: развитие имеющегося demo, release packaging и onboarding. Не ставить в README будущие пользовательские команды до их реализации и проверки.

## Обязательные гарантии

- Нет silent enable интеграций из-за установленного SDK или legacy defaults после explicit disable.
- Нет подстановки `primary` вместо фактического destination.
- Нет смешивания конфигураций, token store, cooldown и consent двух экземпляров.
- Нет повторных фактов/отправок при retry, restart и shadow processing.
- Pending/inferred не становятся подтверждёнными observed без действия владельца.
- Нет обработки истории моделью или отправки в канал вне разрешённых категорий.
- Источники, выбранные пакеты и custom definitions сохраняют свои версии и происхождение.
- Старые важные HF regression tests остаются; новый зелёный тест не считается заменой старого invariant.

## Проверка и отчёт

Использовать disposable PostgreSQL/TimescaleDB по правилам репозитория. Отдельно запускать core-only и full synthetic конфигурации. Любые browser/live tests явно отделять от unit/DB checks. Не сообщать число тестов без лога конкретного запуска и SHA.

В результате PR/report должны быть: что изменено; путь нового пользователя/контрибьютора, который теперь работает; тесты и команды; scope оставшейся работы; миграционный риск; совместимость; подтверждение отсутствия личных данных/секретов в diff.

Конечный критерий всего этапа: внешний разработчик добавляет поддерживаемое расширение без форка ядра, а пользователь получает законченный повседневный сценарий без правок исходников. Одного интерфейса, одного mock или количества merged PR недостаточно.
