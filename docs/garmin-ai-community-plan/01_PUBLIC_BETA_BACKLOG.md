# План следующего этапа: публичная бета и расширяемость

Основа: main `8d9bd0208da5891f836ce7045004ef729fa40aab`. Это предлагаемый backlog, не реализованные изменения. CP-задачи не закрывают автоматически GA/UNI/HF. Сначала проверить, не выполнены ли части в новом main.

## CP-01 — Разрешить переиспользование и открыть человеческий contribution flow

**Приоритет:** P0 для публичного распространения. **Зависимости:** решение правообладателя о лицензии.

**Почему:** лицензия не объявлена; CONTRIBUTING ориентирован на процесс агента, а не внешнего разработчика (R01–R03, R15).

**Работа:**
- Предложить владельцу Apache-2.0 как выбранный вариант; проверить права на код, заимствования, лицензии прямых/транзитивных зависимостей и поставляемых образов. Не приписывать лицензию чужим компонентам.
- После решения добавить LICENSE, metadata и необходимые third-party notices. Не делать автоматическое лицензирование от имени владельца.
- CONTRIBUTING: быстрый синтетический запуск, карта модулей, четыре вида вклада, как получить ревью, кто принимает изменения. Убрать из публичных требований обязательные платные инструменты и предположение о праве новичка самостоятельно merge.
- Внутренние инструкции для coding agents оставить в AGENTS/maintainer guide, не ослабляя проверку безопасности.
- Подготовить SECURITY с приватным способом сообщения об уязвимости, правила общения, issue templates и короткие правила обработки чувствительных вложений.

**Приёмка:** независимый разработчик понимает лицензию, запускает тест и создаёт PR без Garmin/Telegram/LLM credentials. Maintainer утверждает лицензию. На публичной странице явно указано отсутствие аффилиации с Garmin; название не даёт ложной официальности.

## CP-02 — Матрица возможностей и один актуальный публичный roadmap

**Приоритет:** P0. **Зависимости:** нет.

Разделить наличие реализации, синтетические проверки, live-проверки и поддерживаемый release. Для источника указывать доступные метрики, raw/canonical/query support, формат, ограничения времени, дату и версию проверки; без данных конкретного аккаунта. Для канала — вход, ответ, формы, edits, voice, инициативы, receipts. Для модели — structured extraction, tools, язык, audio, лимиты и privacy scope.

Сверить актуальные HF regression cases с опубликованной версией. Критические privacy/correctness-ошибки блокируют соответствующий публичный сценарий. Не повторять ошибку «пройден тест application service, значит пройден весь транспорт».

**Приёмка:** у каждого публичного обещания есть capability status и ссылка на доказательство с SHA. Остатки из R18 остаются видны. Исторические отчёты не выдают состояние прошлой ветки за сегодняшний roadmap. Страница на английском и русский перевод имеют одну область обещаний.

## CP-03 — Registry действительно управляет runtime

**Приоритет:** P0 инженерный. **Зависимости:** CP-02.

**Точки:** `integrations.py`, `runtime.py`, `config.py`, `onboarding.py`, provider/channel lifecycle, jobs и consent.

Заменить явный выбор `configured_instance(..., "gemini")`, Telegram startup и Garmin job branches механизмом разрешения зарегистрированных адаптеров. Не переносить центральный if/else в другой центральный файл. Официальные адаптеры реализуют стабильные Source/Channel/Model-контракты, а composition root знает kind и capabilities.

Ввести конфигурацию и secret references на уровне экземпляра интеграции. Старые GA_* переменные проходят совместимый перевод в именованные default instances; они не исчезают молча. ID участника разговора не заменяет внутреннего владельца. Интеграции не создаются только потому, что SDK установлен. Конфигурация disabled/пустой allowlist имеет явный смысл.

Сохранить restart, rate-limit, fencing, cancellation, uncertain delivery, disable/consent revalidation. Во время миграции один путь выполняет side effects; shadow-path только сравнивает результат. Не дублировать отправки и изменения дневника.

**Приёмка:** установка тестового extension package и его явное включение запускают адаптер через обычный application lifecycle без правок core/runtime; удаление пакета не ломает локальный дневник. Два экземпляра одной интеграции не разделяют credentials, cooldown, адресата и согласия. Старая рабочая конфигурация проходит upgrade.

## CP-04 — Полноценное демо без аккаунтов и секретов

**Приоритет:** P0 продуктовый. **Зависимости:** CP-02; не требует завершения CP-03.

Развить существующий dashboard demo (R11), не создавать параллельный UI. Синтетический профиль содержит согласованные события, наблюдения, пропуски и заведомо исправляемую запись. Человек создаёт многополевой трекер, записывает факт, видит историю и анализ, исправляет факт, видит обновление.

По умолчанию никакого внешнего LLM/мессенджера и скрытых сетевых обращений. Детерминированные ответы/демо-транскрипт явно помечены; не выдавать их за живой AI. Внешнюю модель можно подключить отдельно с согласием. Demo storage строго отделён от personal storage; reset не затрагивает личные данные. Статический публичный demo, если будет размещён, не принимает личные данные.

**Приёмка:** новый человек понимает пользу до Garmin login. Тесты проверяют не только backend, но и действия в браузере. Снимки и видео для README получают данные из той же фикстуры.

## CP-05 — Установка и обновление для пользователя, не для разработчика

**Приоритет:** P0 продуктовый. **Зависимости:** CP-01, CP-02, CP-04 для публичного релиза.

Предоставить versioned release и проверенный образ, совместимые manifest/Compose и onboarding. Сборка из source остаётся dev-путём. Выбрать поддерживаемые платформы по фактическим тестам; проверить amd64/arm64 до заявления о поддержке. Проверить совместимость лицензий поставки, включая БД/образы, отдельно от лицензии собственного кода.

Интерактивно: язык/часовой пояс → demo или личное хранилище → сценарии/свой трекер → необязательные источники → необязательный канал → необязательная модель → категории согласия → статус импорта. Секреты вводятся локально, не в публичный чат. Это не обещание полностью бездействующего Garmin onboarding: MFA и ограничения внешнего сервиса могут требовать владельца.

Обновление: backup, проверка схемы/версий плагинов, миграция, restart, smoke test; откат только совместимым кодом или восстановлением проверенного снимка. Диагностика отличает healthy API, работающую очередь и свежие данные.

**Приёмка:** чистая установка по пользовательской инструкции без Python toolchain на хосте там, где применяется опубликованный Docker образ; повторная настройка сохраняет ключи и историю. Реальная конфигурация не требует редактирования исходников. Публичный release manifest привязан к SHA и содержит поддерживаемые пути обновления.

## CP-06 — Три завершённых сценария и обмен пакетами

**Приоритет:** P1. **Зависимости:** CP-02, CP-04.

Использовать текущие tracker/definition/pack services. Подготовить:
1. Сон и субъективная энергия: данные Garmin + собственная оценка, без диагноза.
2. Бег и субъективная тяжесть: сохранённая активность + сообщённое усилие, честная сопоставимость.
3. Концентрация/прогулки: пользовательский трекер, пригодный без Garmin.

Каждый пакет содержит определения и их версии, единицы/шкалы, подписи, предлагаемые формы и отключённые по умолчанию инициативы, допустимый AnalysisSpec и объяснение ограничений. Кофеин и головная боль остаются необязательными специализированными пакетами. Не считать автоматически любой набор метрик валидированной моделью здоровья.

Экспорт пакета не включает данные, переписку, identity, GPS, credentials или destination bindings. Импорт показывает diff, permissions и конфликты версий; не включает внешние передачи или напоминания без подтверждения. Рецепт аналитики — данные и разрешённые операции, не Python/SQL/prompt с неограниченными полномочиями.

**Приёмка:** независимый человек импортирует пакет и адаптирует поля без SQL/code changes. Два пакета не переопределяют системные правила и чужие метрики. Исторические записи продолжают читать старые определения.

## CP-07 — SDK, starter packages и contract-test kit

**Приоритет:** P1, путь контрибьютора. **Зависимости:** CP-03.

Опубликовать версию контракта, migration/deprecation policy, capability schema и минимальные runnable examples: источник, канал, модель, декларативный пакет. Предложенный способ discovery — Python entry points плюс явный allowlist; финальное имя группы выбирается с учётом принадлежности namespace (E06).

Контрибьютор не получает прямой production engine/SQLAlchemy Session или все секреты. API SDK предоставляет нужные bounded operations; при этом честно указать: in-process Python plugin является доверенным кодом с возможностями процесса, интерфейс SDK не создаёт sandbox. Непроверенные code plugins не ставятся автоматически. Для настоящей изоляции нужен отдельный process/container с ограничением FS/network, это отдельная архитектурная гарантия.

**Приёмка:** пример запускается из отдельного пакета на опубликованной версии без fork; CI выполняет TCK на синтетике. Минимум один внешний разработчик воспроизводит путь. Версии и capabilities содержат проверенные факты, а не просто bool ready.

## CP-08 — Второй реальный модельный backend

**Приоритет:** P1. **Зависимости:** CP-03, CP-07, политика CP-02.

Мой выбор для проверки независимости — локальный Ollama backend с JSON-schema structured outputs (E05), а не ещё одна Gemini-модель. Поддерживать конкретную протестированную конфигурацию/модель; одинаковая форма HTTP не доказывает одинаковые ответы. Не обещать перенос transcription, tool calling и streaming без проверки capability.

Согласие относится к экземпляру и назначению. Локальный режим не переключается на облако при ошибке без отдельного явного согласия. Диалог, extraction, статистика и хранение остаются общими. Модель предлагает операции, сервер валидирует и исполняет их.

**Приёмка:** одна и та же синтетическая задача создания/уточнения/анализа проходит через оба backend с одинаковыми доменными гарантиями. Оценить задержку и расход ресурсов на выбранном hardware; не обещать конкретную скорость заранее. Неправильные схемы, выдуманные числа, 429, timeout, большие ответы и отозванное согласие не портят дневник. Локальный backend не обязательно поддерживает голос.

## CP-09 — Реальный второй канал: локальный web-chat

**Приоритет:** P1. **Зависимости:** CP-03, CP-07.

Не реализовывать WhatsApp/Viber в этом этапе. Использовать локальный аутентифицированный web-chat как реальный второй вход в тот же агент: текст → команда/форма → изменения → анализ → outbox → UI. Сохранить Telegram и limited reference adapter. В отличие от reference mock, проверять настоящий HTTP/WebSocket/SSE ingress выбранной реализации и браузерный UI.

Прямой доступ к внутренней функции в тесте недостаточен для доказательства работы двух каналов. Непрочитанные инициативы локального web-chat не объявляются доставленными в закрытый браузер; поддержки push не заявлять без реализации.

**Приёмка:** одинаковые пользовательские истории проходят реальный Telegram handler с подменой внешнего Bot API и настоящий локальный web ingress. Каналы изолируют pending clarification/reply context; общие факты синхронно видны обоим, только при разрешении. Правки, пауза, отзыв согласия и restart не создают дубликатов.

## CP-10 — Расширяемый источник + безопасный файловый импорт

**Приоритет:** P2, первый source contribution. **Зависимости:** CP-03, CP-07.

Довести SourceAdapter до сохранённого курсора, identity, raw/provenance, time semantics, capability availability, retry и удаления/исправления. Первым независимым примером может быть строгий CSV/JSON import пользовательских наблюдений. Это не заявленная поддержка Apple Health, Google Health Connect или официального Garmin export ZIP — такие форматы требуют отдельных адаптеров.

Предпросмотр mapping: дата/время, timezone, единицы, шкала, source ID, формат десятичных чисел, отрицательные/sentinel значения. Не угадывать timezone или единицы при неоднозначности. Import имеет immutable file hash, row identity, preview и идемпотентную запись; пользовательские исправления не затираются повторным импортом.

**Приёмка:** импорт плюс повтор/restart не дублирует наблюдения. В анализе виден источник. Данные разных владельцев/устройств не объединяются по одинаковому числу или timestamp. При ошибке строки получаем ограниченный redacted report, не публикацию исходника.

## CP-11 — Независимая эксплуатационная приёмка

**Приоритет:** P0 для объявления поддерживаемого release. **Зависимости:** CP-02, CP-05; применимо по готовности каждой интеграции.

Использовать существующий R18-протокол вместо новой несвязанной системы. Отдельно проверить исправления HF, непрерывную работу, ошибки сети/БД, heartbeat и реальный progress, восстановление без повторной отправки outbox, источник истины для consent и pause, лимит стоимости AI, disk/backup.

**Приёмка:** воспроизводимые синтетические fault-тесты + добровольный семидневный запуск + восстановление на независимом host. Все live-вызовы и передача backup — отдельное решение владельца тестовой установки. Публичный отчёт содержит версии, агрегированные технические показатели и ограничения, не личные ряды и не секреты. Нет наблюдения — нет отметки passed.

## CP-12 — Пилот и продвижение по результатам

**Приоритет:** P1, старт небольшой группы после CP-01/02/04; расширение после CP-05/11.

Набрать 5–10 добровольных пользователей и 2–3 потенциальных контрибьюторов. Отдельные self-hosted установки, никаких аккаунтов на сервере автора по умолчанию. Дать одинаковую инструкцию и наблюдать трение, не проходить setup вместо участника.

Публичные материалы: короткое synthetic demo, три конкретных сценария, поддерживаемые integration badges, честные ограничения, Quick Start, contribution path. Начинать с Garmin/self-hosted/quantified-self и Python-сообществ, соблюдая правила площадок; тексты адаптировать к конкретной группе. Не использовать массовую рассылку, накрутку звёзд или медицинские обещания.

**Приёмка:** доступны журнал препятствий, время до первого результата, результат на день 7 и причины прекращения использования; ручной/opt-in сбор без содержимого дневника. Внешний PR проходит человеческое ревью. Следующий roadmap меняется по повторяющимся проблемам, не по одному громкому пожеланию.
