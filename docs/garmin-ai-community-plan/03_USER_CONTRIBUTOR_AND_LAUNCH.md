# Пользователь, контрибьютор и публичный запуск

## А. Путь нового пользователя

На первой странице объяснить результат: сохранить историю устройств и свои записи, задавать вопросы по этим данным, выбирать где общаться и какая модель может их обрабатывать. Отдельно показать сегодняшнюю поддержку, экспериментальные интерфейсы и будущие направления.

Три входа, не одна длинная инструкция:

1. **Посмотреть демо:** синтетические данные без регистрации, API key и риска испортить личную историю.
2. **Установить себе:** versioned release, локальное хранилище, пошаговый setup, необязательные подключения.
3. **Разработать расширение:** synthetic starter и выбранная задача, не onboarding личного Garmin.

Сохранить существующий dashboard и проверить актуальность его документации: историческое описание первой read-only поставки не должно ограничивать или неверно описывать текущие формы.

### Первые действия в личной установке

Язык, timezone и units; выбор готового сценария или пустого трекера; история источника с прогрессом и честным unknown horizon; подключение одного канала; необязательная модель и обзор передаваемых категорий; первый факт и первый подтверждаемый ответ.

Требования:
- Человек может закончить setup без Garmin, Telegram и LLM.
- Не нужно включать мигрени, кофеин или бег, если это не его цель.
- Новая модель/канал не получают sensitive schemas/facts только из-за установки.
- Сбой Garmin/модели не запрещает запись фактов и просмотр сохранённых данных.
- В статусе различаются job выполнен, fetch успешен, последнее наблюдение и полнота интервала.
- Запись содержит источник и временной смысл; дата дня не выдумывает время события.
- Можно исправить, удалить, экспортировать, отключить инициативы и увидеть причину ограничения.

## Б. Три демонстрации, которые стоит завершить

### Сон и самочувствие

Пользователь отмечает субъективную энергию и сопоставляет её с уже сохранённым сном. Демонстрация показывает число наблюдений, пропущенные дни и возможность различия субъективной оценки с оценкой часов. Не обещает диагностики или причинной связи.

### Тренировка и субъективная тяжесть

Система показывает сохранённую активность, предлагает внести RPE и сравнивает сопоставимые тренировки. После correction пересчитывается результат. Не выдаёт один средний пульс/темп за универсальную оценку здоровья.

### Собственный трекер без устройства

«Работа без отвлечений»: интервал, шкала концентрации, количество отвлечений, заметка. Человек создаёт это через UI/диалог и использует без изменения кода. Счётчики суммируются только при правильной семантике; разные версии шкал не смешиваются.

Каждый пример использует существующие services, а не demo-only алгоритм. Демо-ответы без LLM явно подписаны. Не создавать специально красивую, но невоспроизводимую историю.

## В. Путь первого вклада

Контрибьютор должен получить один ограниченный результат за один PR. Четыре вида вклада:

- декларативный пакет/перевод/пример;
- адаптер источника или импортёр;
- адаптер канала или модельный backend;
- regression/UX/документация.

Публичный CONTRIBUTING объясняет окружение, тесты, структуру, рамки PR и ожидания ревью. Инструкция `@codex review` может остаться инструментом maintainers, но не условием права участвовать. Право merge принадлежит назначенным maintainers, а не автоматически любому автору PR.

### Предлагаемые первые открытые issues

Это заготовки, не уже созданные GitHub issues:

| Задача | Что получит контрибьютор | Проверяемый итог |
|---|---|---|
| Проверить чистый setup на заявленной платформе | Инструкция и synthetic профиль | Исправленный конкретный шаг и воспроизводимый отчёт без секретов |
| Подготовить EN/RU описание пакета концентрации | Схема, fixture, допустимые labels | Совпадающий смысл и IDs при переключении языка |
| Добавить пример исправления пользовательской записи | UI/handler path и regression fixture | Повтор команды не создаёт дубликат |
| Документировать одну capability канала | Формат matrix и test reference | Честные supported/unsupported cases |
| Улучшить сообщение об отсутствующем SDK | Один установленный/отсутствующий модуль | Core запускается, ошибка понятна пользователю |
| Добавить edge case файлового импорта | Mapping contract и синтетический CSV | Неоднозначная timezone не угадывается |
| Написать документацию безопасного экспорта пакета | Готовый allowlisted export path | Ни одного идентификатора/факта/токена в экспортируемом примере |
| Исправить доступность формы с клавиатуры | Один экран и browser test | Полный проход без мыши и без новой UI-архитектуры |

Не называть сложный переход всего runtime задачей good first issue. Не закрывать issue одним большим автогенерированным PR без ясной проверки. Один label good-first-issue не заменяет описание входа, выхода и теста.

## Г. Документация и витрина

Предлагаемая навигация: Overview → Try demo → Install → First useful result → Connect Garmin/Telegram/model → Custom trackers → Data/privacy/backup → Troubleshooting → Build an extension → Contribute.

Главный README коротко показывает проблему, результат, synthetic screenshot/video, текущую поддержку, три входа и ограничения. Детали исторических GA/UNI/HF проверок остаются доступными, но не заменяют пользовательское руководство.

Для доверия нужны: лицензия, конкретная версия release, опубликованные ограничения, поддерживаемые ОС/архитектуры, секреты/retention/consent, способ сообщить об уязвимости, upgrade/restore guide. Нельзя обещать медицинскую надёжность или абсолютную приватность всех внешних интеграций.

Topics, описание репозитория и Discussions — полезная навигация, не самодостаточный механизм роста. Не считать, что изменение названия или числа keywords автоматически привлечёт людей.

## Д. Пилот

Предложение: 5–10 пользователей и 2–3 контрибьютора. Это желаемая выборка пилота, не расчёт статистической репрезентативности.

**На входе:** запланировать scope, дать одну опубликованную инструкцию; не заставлять делиться исходными рядами и не собирать пароли. Отметить уже имеющиеся Docker/технические навыки, чтобы не смешивать разные типы проблем.

**Первая сессия:** понял ли человек назначение; запустил ли демо; смог ли создать свой трекер; завершил ли реальную настройку; где понадобилась помощь; получил ли результат, который считает полезным.

**На день 7:** использует ли историю/вопросы; не раздражают ли инициативы; знает ли про исправления, экспорт и отключение AI; что сломалось; почему перестал использовать.

**Метрики:** время до первого useful result, доля завершённых установок, объём помощи автора, доля корректно законченных операций, частота непонятных ошибок, возвращение на день 7, количество законченных внешних вкладов. Собирать вручную или opt-in без содержимого health data; диагностический экспорт должен иметь preview.

Пример предлагаемых gates: 4 из 5 установок без правок исходников; 2 независимых успешных contribution flow; 0 известных необработанных критических consent/correctness-блокеров в заявленном сценарии. Это не обещание отсутствия всех ошибок.

## Е. Продвижение

Сначала небольшой pilot announcement с честной просьбой протестировать конкретный сценарий. После исправления повторяющихся препятствий — public beta release с демонстрацией и списком законченных кейсов.

Сообщение для Garmin-аудитории показывает дополнительный контекст, которого нет в данных часов. Для self-hosted аудитории — собственное хранилище, переносимость и управление внешней обработкой. Для Python/open-source разработчиков — пример адаптера, стабильный контракт и задача с тестом. Не отправлять одинаковую рекламу массово на все площадки.

Сбор пакетов и исправлений от пользователей создаёт ценность только при понятном импорте и совместимости. Не строить marketplace раньше каталога проверенных data-only примеров. Масштабирование команды начинается с maintainers для реальных используемых адаптеров, а не с обещания поддерживать каждый мессенджер лично.

## Ж. Условия внешних каналов

WhatsApp Business Platform и Viber имеют собственные правила и процедуры. На момент исследования WhatsApp ограничивает свободные ответы 24-часовым customer-service window и требует approved templates вне окна; политика также предъявляет требования к consent и обработке health information. Viber сообщает о коммерческих условиях создания новых bots с 2024-02-05 (E03–E04).

Следствие для дизайна: перед подключением будущего канала нужен capability + policy review, а не флаг «умеет отправлять текст». Архитектура может допускать канал, который не разрешает произвольный проактивный вопрос. Допустимость конкретного deployment/AI use case здесь не установлена.
